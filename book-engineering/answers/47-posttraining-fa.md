# پاسخ‌نامهٔ تشریحی فصل ۴۷

این پاسخ‌نامه مستقل از متن فصل است. نمونه‌ها برای توضیح قراردادها هستند؛ نتیجهٔ fixture یا مدل کوچک را نباید به کیفیت مدل دیگری تعمیم داد.

## پاسخ تمرین ۱ — ادامهٔ پیش‌آموزش در برابر SFT

در ادامهٔ پیش‌آموزش دامنه‌ای، ورودی معمولاً متن پیوسته از دامنهٔ انتخاب‌شده است و هدف causal language modeling پیش‌بینی توکن بعدی در متن است. در SFT، رکورد معمولاً دستور/پرسش و demonstration پاسخ هدف را دارد؛ اگر prompt فقط زمینه باشد، labelهای آن از loss کنار می‌روند و target پاسخ تحت نظارت قرار می‌گیرد. یکی ممکن است از corpus خام و دیگری از زوج‌های نمایشی استفاده کند، هرچند طرح‌های واقعی می‌توانند پیچیده‌تر باشند.

برای بازتولید، عبارت «fine-tuning» کافی نیست؛ باید checkpoint پایه و revision، tokenizer، نوع داده، هدف و mask، splitها، مقدار token/updates، schedule، نسخهٔ وابستگی‌ها، معیارها و تصمیم‌های validation معلوم باشند. همچنین باید روشن شود test چه زمانی و چند بار دیده شده است.

## پاسخ تمرین ۲ — labelهای causal

اگر دنباله `BOS + چهار token prompt + سه token پاسخ + EOS` باشد، در ساده‌ترین قرارداد labels چنین است:

```text
input_ids = [BOS, p1, p2, p3, p4, y1, y2, y3, EOS]
labels    = [-100,-100,-100,-100,-100, y1, y2, y3, EOS]
```

مدل به کمک prompt پاسخ را پیش‌بینی می‌کند، اما prompt خود target loss نیست. اگر `p1…p4` در labels باقی بمانند، مدل علاوه بر پاسخ، برای بازتولید prompt هم جریمه/پاداش می‌گیرد؛ این دیگر همان objective موردنظر نیست. در عمل causal LM معمولاً logits را یک موقعیت نسبت به labels شیفت می‌دهد؛ پس شمار و جایگاه هدف معتبر را با قرارداد همان مدل بررسی کنید.

## پاسخ تمرین ۳ — split بر پایهٔ سند مادر

اگر هر سند مادر سه قطعه داشته باشد و هر قطعه جداگانه بین train و test پخش شود، مدل ممکن است عبارت‌ها، ساختار یا اطلاعات یک سند را در train ببیند و نسخهٔ نزدیکش را در test. این هم‌پوشانی باعث می‌شود test کمتر مستقل باشد. برای split از `group_id` یا شناسهٔ پایدار سند مادر استفاده می‌کنیم تا همهٔ قطعه‌های وابسته در یک split بمانند.

پس از تثبیت groupها، فقط train برای گرادیان است؛ validation برای تصمیم‌های ازپیش‌تعریف‌شده به‌کار می‌رود؛ testِ held-out پس از پایان انتخاب روش برای گزارش استفاده می‌شود. اگر هم‌پوشانی نزدیک یا منبع مشترک وجود دارد، آن را جداگانه ممیزی و ثبت می‌کنیم؛ فقط برابر بودن group_idهای فعلی، آلودگی ناشناخته را رد نمی‌کند.

## پاسخ تمرین ۴ — چرا ۱٬۰۰۰ نمونه قانون نیست؟

اول، مقالهٔ LIMA از مدل پایه، دادهٔ curated، taskها، promptها و معیارهای مشخص خود استفاده کرده است؛ تعداد نمونه به همان setup وابسته است. دوم، اندازهٔ نمونه تعداد token، تنوع، کیفیت، زبان، پوشش وظایف یا تناسب هدف را مشخص نمی‌کند؛ هزار پاسخ کوتاه با هزار سند بلند برابر نیستند. علاوه بر این، تغییر checkpoint یا ارزیابی می‌تواند نتیجه را عوض کند.

یک ablation قابل‌دفاع می‌تواند یک baseline ثابت و چند زیرمجموعهٔ ازپیش‌تعریف‌شده با کیفیت/تنوع متفاوت داشته باشد. برای هر run مدل پایه، tokenizer، schedule و تعداد update را ثابت نگه دارید؛ منبع و tokenها را ثبت کنید؛ انتخاب را فقط با validation انجام دهید؛ سپس test مستقل را یک بار پس از تثبیت پروتکل گزارش کنید. چند نمونهٔ خطا و عدم‌قطعیت را هم بررسی کنید. این آزمایش دربارهٔ مدل و دادهٔ خودتان نتیجه می‌دهد، نه قانون عمومی.

## پاسخ تمرین ۵ — مجوز مدل، داده و revision

metadata مجوز مدل‌کارت دربارهٔ artifact مدل است؛ خودبه‌خود وضعیت حقوقیِ داده‌های pretraining، datasetهای downstream یا یک کاربرد خاص را تعیین نمی‌کند. کارت Pythia-14m در تاریخ بازبینی metadata را Apache-2.0 گزارش می‌کرد، ولی این پاسخ نه آن را به تضمین حقوق داده تبدیل می‌کند و نه جای بررسی شروط را می‌گیرد.

پروژه شناسهٔ `EleutherAI/pythia-14m` را به SHA `cf967c0a9a04383db6f7b1108d86b2962634b4ac` pin می‌کند؛ در نتیجه به `main` متحرک متکی نیست. کارت مدل آن را English و پژوهشی معرفی می‌کند و برای زبان‌های دیگر یا deployment توصیه نمی‌کند. پس از این آزمایش کوچک نمی‌توان کیفیت فارسی، آمادگی محصول یا مجوز استفادهٔ دیگری را استنتاج کرد.

## پاسخ تمرین ۶ — validation و test

Validation بخشی از فرایند توسعه است: می‌تواند برای مقایسهٔ checkpoint، prompt یا تنظیماتی که در پروتکل آمده‌اند استفاده شود؛ هر بار باید ثبت شود چه تصمیمی با دیدن آن گرفته شد. Test برای گزارش نهایی است و اگر بعد از هر تغییر بررسی شود، دیگر شاهد مستقل نیست. Test را از انتخاب threshold، prompt یا mixture دور نگه دارید و پس از تثبیت روش یک‌بار گزارش کنید. اگر test برای انتخاب استفاده شد، آن را چنین اعلام کنید و یک ارزیابی مستقل تازه لازم بدانید.

## پاسخ تمرین ۷ — template در برابر mask

Chat template تعیین می‌کند پیام‌ها، نقش‌ها و tokenهای مرزی چطور سریال‌سازی شوند؛ loss mask تعیین می‌کند کدام tokenها target آموزش‌اند. ممکن است قالب درست باشد اما labels به اشتباه پیام user را هم هدف بگیرند؛ یا mask ظاهراً درست روی رشتهٔ خام پس از tokenization به جای نادرستی بیفتد. باید tokenizer/template همان مدل و نسخه را به‌کار برد، یک نمونه را token به token بازبینی کرد و نقش‌ها، پایان turn، padding و شمار targetها را دید.

## پاسخ تمرین ۸ — `-100` در برابر `attention_mask`

`attention_mask` معمولاً مشخص می‌کند کدام موقعیت‌های ورودی برای attention فعال‌اند؛ `labels=-100` در قرارداد `CrossEntropyLoss` جایگاه‌هایی را از objective حذف می‌کند. این‌ها دو وظیفهٔ متفاوت‌اند. اگر padding از attention mask کنار گذاشته شود اما label آن هنوز معتبر باشد، ممکن است padding همچنان target loss شود. در batch لازم است هم mask توجه و هم mask هدف را با هم، و با پیاده‌سازی واقعی trainer، بررسی کنیم.

## پاسخ تمرین ۹ — domain adaptation به‌تنهایی نتیجه نیست

نام DAPT یا TAPT توصیف نوع دادهٔ ادامه‌دار است، نه تضمین بهبود. نتیجه به مدل، domain، اندازه و کیفیت corpus، tokenization، schedule و task evaluation وابسته است. برای آزمایش، baseline و دادهٔ ادامه‌دار را دقیق تعریف کنید، runها را تا حد ممکن کنترل کنید و metricهای هدف و taskهای جانبی را روی splitهای جدا بسنجید. نتیجهٔ یک مقاله را با برچسب setup آن نقل کنید، نه نسخهٔ آمادهٔ همهٔ مدل‌ها.
