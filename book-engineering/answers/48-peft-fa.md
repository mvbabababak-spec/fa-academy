# پاسخ‌نامهٔ تشریحی فصل ۴۸ — PEFT، Adapter، LoRA و QLoRA

پاسخ‌ها نمونهٔ استدلال‌اند، نه تنها صورت‌بندی ممکن. همهٔ عددها به ابعاد فرض‌شده در تمرین مربوط‌اند؛ از آن‌ها نمی‌توان اندازهٔ VRAM یا کیفیت یک مدل واقعی را نتیجه گرفت.

## تمرین ۱ — شمار پارامتر LoRA

برای `d_in=2048`, `d_out=8192`, `r=8`:

- `A` شکل `8 × 2048` دارد: `16,384` پارامتر.
- `B` شکل `8192 × 8` دارد: `65,536` پارامتر.
- جمع عوامل: `r(d_in+d_out) = 8 × 10,240 = 81,920`.
- ماتریس کامل: `2048 × 8192 = 16,777,216` خانه.
- نسبت: `81,920 / 16,777,216 ≈ 0.0048828`، یعنی حدود `0.4883%` برای همین یک ماتریس.

این نسبت bias، moduleهای دیگر، task head، وزن‌های trainable بیرون LoRA و activation/optimizer را در بر نمی‌گیرد. اگر چند projection در هر یک از چند بلوک هدف گرفته شوند باید تعداد همان ماژول‌ها جمع شود.

## تمرین ۲ — adapter bottleneck

برای یک bottleneck ساده با `d=1024` و `m=32`، فقط وزن‌های دو projection `2dm = 2 × 1024 × 32 = 65,536` است. این عدد biasهای احتمالی، LayerNorm، تعداد adapterهای هر بلوک، نوع قرارگیری، headهای task و جزئیات معماری را حذف می‌کند. مقالهٔ Houlsby دو جایگاه adapter در هر بلوک BERT خود داشت؛ مدل‌های دیگر الزاماً همان طرح را ندارند. همچنین parameter count معادل latency یا اندازهٔ فایل mergeشده نیست.

## تمرین ۳ — payload خام چهار بیتی

`4,000,000,000 × 4 / 8 = 2,000,000,000` بایت، یعنی 2 GB ده‌دهی (حدود 1.86 GiB دودویی). این فقط payload packed در محاسبهٔ ایده‌آل است. حافظهٔ واقعی علاوه بر آن می‌تواند شامل scaleها و metadataهای block quantization، لایه‌های خارج از quantization، adapterها، optimizer state آن‌ها، activationها، gradientها، workspaceهای موقت، alignment و fragmentation باشد. بنابراین این محاسبه نه VRAM اندازه‌گیری‌شده است و نه پیش‌بینی کامل حافظه.

## تمرین ۴ — projection تجمیع‌شده

ابتدا معماری و نسخهٔ مدل را pin می‌کنم؛ سپس `named_modules()`، شکل weightها و پیاده‌سازی attention را بازبینی می‌کنم تا بدانم `qkv_proj` واقعاً خروجی‌های Q/K/V را چگونه ترکیب می‌کند. پس از اعمال PEFT، شمار لایه‌های wrap‌شده و تعداد trainable parameters را با انتظار مقایسه می‌کنم و یک forward/backward کوچک روی batch مصنوعی اجرا می‌کنم. اگر fused module جداگانه قابل هدف‌گیری نباشد، باید از API پشتیبانی‌شدهٔ همان نسخه یا روش تفکیک/targeting مناسب استفاده و دوباره آزمایش کرد؛ نام‌های `q_proj` از مدل دیگری را نمی‌توان بی‌بررسی کپی کرد، چون ممکن است هیچ لایه‌ای را هدف نگیرد یا ماژول نامناسبی را wrap کند.

## تمرین ۵ — مقایسهٔ LoRA و QLoRA

مدل پایه و revision، tokenizer، داده و hash، split/group، template، context length، معیار، وظیفه، تعداد update و پروتکل انتخاب باید یکسان یا تفاوتشان صریح باشد. در دو پیکربندی LoRA و QLoRA، rank، alpha/variant، target modules، dtype، quantization و optimizer را ثبت می‌کنم. پارامترهای trainable و اندازهٔ adapter را از peak حافظهٔ allocated/reserved، throughput و latency جدا گزارش می‌کنم؛ همهٔ سنجش‌های سخت‌افزاری را روی همان دستگاه، نسخهٔ driver/backend و روش warm-up انجام می‌دهم. Validation می‌تواند برای انتخاب config مصرف شود؛ test پس از تثبیت تصمیم‌ها برای گزارش نهایی یک‌بار استفاده می‌شود. ادعای «بهتر» فقط به task، سنجه، جمعیت و تنظیم‌های سنجیده‌شده محدود می‌ماند.

## مرز پاسخ‌نامه

این پاسخ‌ها پروتکل طراحی و حساب ماتریسی را تمرین می‌دهند؛ هیچ PEFT/QLoRA مدل واقعی اجرا نشده و هیچ benchmark یا ارزیابی کیفیت از این محاسبات به دست نمی‌آید.
