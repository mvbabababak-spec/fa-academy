# پاسخ‌نامهٔ مستقل فصل ۶۱ — سرو و بهینه‌سازی استنتاج

این پاسخ‌نامه صورت هر تمرین را کامل بازگو می‌کند و نمونه‌ای از استدلال قابل‌ممیزی می‌دهد. پاسخ نهایی برای هر سخت‌افزار، نسخه، workload و کاربرد باید با شواهد همان محیط اصلاح شود؛ هیچ پاسخ زیر benchmark یا پیشنهاد تولیدی برای یک مدل مشخص نیست.

## ۱. ماتریس سازگاری دو runtime

**پرسش:** تیمی یک checkpoint موجود و دو گزینهٔ runtime، vLLM روی GPU سازمانی و llama.cpp در build فعلی، دارد. ماتریس مدل/قالب/دستگاه و آزمون صحتی پیشنهاد دهید که پیش از benchmark انجام می‌دهید.

**پاسخ:** ابتدا checkpoint را با revision/hash کامل، config، tokenizer، chat template و مجوز ثبت می‌کنم؛ سپس نسخهٔ دقیق vLLM، نسخه و flags ساخت llama.cpp، مدل دقیق GPU، driver و backend را می‌نویسم. در ماتریس، ستون‌های «artifact منبع»، «روش load یا export»، «قالب خروجی»، «dtype/quantization»، «توکن‌ساز»، «حد context»، «دستگاه/driver»، «وضعیت پشتیبانی رسمی» و «نتیجهٔ آزمون» را می‌گذارم. برای vLLM باید release منتخب مدل و معماری را پشتیبانی کند؛ برای llama.cpp باید مسیر تبدیل به GGUF، quantization، backend و offload همان build را مشخص کرد. نام runtime به‌تنهایی سازگاری را ثابت نمی‌کند.

پیش از benchmark، روی یک fixture ثابت چند prompt کوتاه/بلند می‌فرستم، template و شناسه‌های token را inspect می‌کنم، خروجی را در decoding ثابت و seed کنترل‌شده مقایسه می‌کنم، و موارد stop token، EOS، پاسخ خالی، خطای طول context و خطای کمبود حافظه را می‌آزمایم. مقایسهٔ دقیق متن همیشه انتظار نمی‌رود، به‌ویژه اگر quantization یا kernel عددی متفاوت باشد؛ اما باید حدود قابل‌قبول کیفیت و رفتار را پیش از زمان‌گیری تعریف کرد. فقط پس از اثبات اجرای درست وارد benchmark می‌شوم.

## ۲. تشخیص TTFT بالا با TPOT ثابت

**پرسش:** در trace فرضی، TTFT p95 زیاد است ولی TPOT p95 تغییر نکرده. سه علت محتمل و سه سنجه یا برش workload برای تمایز آن‌ها بنویسید.

**پاسخ:** نخست، queue/admission می‌تواند درخواست را پیش از شروع محاسبه معطل کند؛ دوم، prompt طولانی یا prefill پرهزینه ممکن است نخستین خروجی را عقب بیندازد؛ سوم، cold start، بارگذاری وزن یا warm/cold prefix-cache می‌تواند به TTFT اضافه کند. چون TPOT پس از نخستین خروجی تغییر نکرده، decode برای درخواست‌های موفق ممکن است ثابت مانده باشد، اما این قرینه به‌تنهایی تشخیص قطعی نیست.

برای تفکیک، TTFT را به queue wait و prefill time جدا می‌کنم؛ طول prompt و prefix-hit را bucket می‌کنم؛ cold و warm run را جدا می‌گیرم و زمان startup را از پنجرهٔ steady-state جدا گزارش می‌دهم. در صورت نبودن سنجهٔ داخلی، فقط می‌توان گفت TTFT مشتری بالا بوده و علت در trace قابل‌شناسایی نیست؛ نباید از TPOT ثابت نتیجه گرفت که backend یا GPU بی‌نقص است.

## ۳. تصمیم دربارهٔ quantization و افت کیفیت

**پرسش:** کمّی‌سازی وزن، حافظهٔ فایل را کم کرده اما چند گروه ارزیابی کیفیت افت کرده‌اند. پروتکل تصمیم rollback/پذیرش و داده‌هایی را که باید جدا نگه دارید شرح دهید.

**پاسخ:** baseline مدل و artifact کمّی‌شده را با hash، config و ابزار/نسخهٔ export جدا ثبت می‌کنم. گروه‌های ارزیابی، promptها، زبان، طول context، decoding و معیارها را پیش از تغییر تعریف می‌کنم؛ پس از تغییر، همان split ثابت را دوباره می‌سنجم و چند بار در صورت تصادفی‌بودن تولید تکرار می‌کنم. میانگین کل کافی نیست: افت گروهی، خطاهای بحرانی، پاسخ‌های عددی، stop behavior و تفاوت طول خروجی را جدا می‌بینم. وزن و KV precision را هم‌زمان تغییر نمی‌دهم، چون انتساب علت دشوار می‌شود.

پذیرش تنها وقتی موجه است که بهبود حافظه یا سنجهٔ runtime از پیش تعیین‌شده باشد و افت کیفیت در حدود قبول‌شدهٔ کاربرد باقی بماند؛ در غیر این صورت artifact قبلی را نگه می‌دارم و rollback می‌کنم. دادهٔ calibration، دادهٔ توسعه، validation و test را از هم جدا می‌کنم و مجوز و منشأ هرکدام را ثبت می‌کنم. اگر test بارها برای انتخاب تنظیمات مصرف شود، دیگر برآورد مستقل کیفیت نیست.

## ۴. محاسبهٔ payload KV

**پرسش:** با ۳۲ لایه، ۸ سر KV، بُعد ۱۲۸، دو بایت برای هر عنصر، ۴٬۰۹۶ token و ۸ دنباله، payload ایده‌آل KV را محاسبه کنید. حداقل چهار مؤلفهٔ خارج از این حساب را نام ببرید.

**پاسخ:** payload برابر است با `2 × 32 × 8 × 128 × 2 × 4096 × 8` بایت. ضریب ۲ برای K و V است. حاصل `4,294,967,296` بایت، برابر ۴ GiB بر مبنای `2^30` بایت است؛ برای یک دنباله ۰٫۵ GiB و برای هر token و هر دنباله ۱۳۱٬۰۷۲ بایت به دست می‌آید.

این یک کف ساده بر اساس full-attention، dtype دو‌بایتی و طول مفروض است. وزن‌های مدل، activationهای دیگر، workspace و bufferهای موقت، metadata بلوک، padding و fragmentation allocator در آن نیستند. همچنین سقف حافظهٔ runtime/driver، graph capture، معماری hybrid یا sliding-window و سربارهای device خارج‌اند. بنابراین ۴ GiB به معنای «برای مدل روی GPU هشت‌دنباله‌ای جا می‌شود» نیست. باید مصرف واقعی، weights و headroom را جدا اندازه گرفت.

## ۵. تحلیل hit پایین prefix cache

**پرسش:** prefix-cache hit پایین است. چه تفاوت‌هایی در prompt، tokenization، block، adapter یا عمر cache را بررسی می‌کنید، و چرا این نتیجه به‌تنهایی ثابت نمی‌کند prefix caching بی‌فایده است؟

**پاسخ:** promptهای واقعی را با hash یا شناسهٔ مجاز بررسی می‌کنم تا معلوم شود بخش آغازین واقعاً مشترک است یا فقط متن ظاهراً مشابه است. tokenizer، chat template، system prompt و tokenهای زمان‌دار/شناسهٔ کاربر را مقایسه می‌کنم؛ یک تغییر کوچک ممکن است tokenهای prefix را تغییر دهد. مرز block، حداقل طول قابل‌cache، سیاست eviction، عمر cache، فضای اشغال و adapter/model identity نیز اهمیت دارند. اگر adapter جزئی از کلید cache باشد، درخواست‌های دو adapter یک cache مشترک محسوب نمی‌شوند.

Hit پایین ممکن است نشان دهد workload پیشوند مشترک ندارد؛ ولی اگر trace کوتاه، cold یا بیشتر درخواست‌ها یکتا باشند، این آزمایش فرصت reuse را ندیده است. آزمایش cold/warm با workload ثابت و سنجه‌های prefill، TTFT، hit/eviction و حافظه لازم است. حتی hit بالا هم به‌تنهایی سود end-to-end را ثابت نمی‌کند؛ باید هزینهٔ اضافی مدیریت cache و tail latency را هم دید.

## ۶. کندشدن speculative decoding در برخی workloadها

**پرسش:** speculative decoding در یک مجموعهٔ prompt سریع‌تر و در مجموعه‌ای دیگر کندتر شده است. نقش پذیرش draft، طول پیشنهاد، هزینهٔ وارسی، batch و کیفیت را در یک آزمایش جداشدنی توضیح دهید.

**پاسخ:** در هر prompt bucket، draft ممکن است تعداد متفاوتی token درست پیشنهاد کند. اگر نرخ پذیرش پایین باشد، محاسبهٔ draft و وارسی target کار اضافه ایجاد می‌کند؛ پیشنهادهای بلند می‌توانند کار target را زیاد کنند، به‌خصوص اگر رد شوند. در batch بزرگ، draft و target هر دو منابع بیشتری می‌خواهند و اثر تعامل scheduling با درخواست‌های دیگر ممکن است از سود هر درخواست بیشتر شود. کیفیت نیز باید جدا کنترل شود: پیاده‌سازی‌های exact rejection ممکن است توزیع هدف را حفظ کنند، اما این را از روی نام feature فرض نمی‌کنم.

پروتکل مناسب یک baseline ثابت و فقط یک حالت speculative دارد؛ مدل، tokenizer، ورودی، decoding و دستگاه تغییر نمی‌کنند. طول draft و اندازهٔ batch را در آزمایش‌های جدا sweep می‌کنم و acceptance rate، TTFT، TPOT، throughput، peak memory، کیفیت و خطا را ثبت می‌کنم. خروجی هر run را جدا نگه می‌دارم و اگر معیار از پیش تعریف‌شده بدتر شد، به baseline برمی‌گردم.

## ۷. طراحی benchmark پیش/پس

**پرسش:** benchmark پیش/پس از تغییر runtime طراحی کنید: workload، warm-up، cache state، نرخ ورود، concurrency، سنجه‌های latency/throughput/memory، ارزیابی کیفیت و محدودیت آماری را مشخص کنید.

**پاسخ:** پیش از اجرا، مدل و artifact/hash، tokenizer/template، runtime/build، GPU/driver، precision، flagها و fixture را ثابت و ثبت می‌کنم. promptها را در bucketهای کوتاه/بلند و خروجی‌ها را با سقف و decoding یکسان می‌سازم. warm-up را جدا از پنجرهٔ اندازه‌گیری اجرا می‌کنم و cold/warm cache را در دو آزمون جدا می‌سنجم. نرخ ورود open-loop و concurrency closed-loop را با تعریف دقیق ثبت می‌کنم؛ اگر فقط یکی سنجیده شود، آن را به دیگری تعمیم نمی‌دهم.

برای هر بار، TTFT، end-to-end، TPOT یا ITL معتبر، request/s، ورودی/خروجی tokens/s، p50/p95/p99، خطا و timeout، صف، cache hit/eviction و peak memory را نگه می‌دارم. ارزیابی کیفیت با split و rubric ثابت و نمونهٔ جدا انجام می‌شود. چند تکرار و تعداد درخواست کافی لازم است؛ percentile روی چند درخواست، tail population را دقیق تخمین نمی‌زند و تفاوت‌های seed، نسخه و دستگاه باقی می‌مانند. نتیجه فقط برای همان workload و tuple گزارش‌شده معتبر است.
