# پاسخ‌نامهٔ مستقل فصل ۶۴ — Red Teaming و امنیت سامانه‌های مولد

پاسخ‌ها نمونهٔ استدلال‌اند، نه حکم واحد برای همهٔ محصولات. هر تصمیم واقعی باید به مجوز، threat model، شواهد، کاربرد، داده و ریسک سازمان وابسته باشد. متن پرسش‌ها در این فایل عیناً با فصل منطبق است.

**صورت پرسش:** یک دستیار RAG را در برابر تزریق مستقیم و غیرمستقیم مقایسه کنید. برای هرکدام نقطهٔ ورود، ناوردای امنیتی و کنترل مستقلی بنویسید که فقط به prompt مدل متکی نباشد.

**پاسخ پیشنهادی:** تزریق مستقیم از ورودی همان کاربر یا رابط وارد می‌شود؛ تزریق غیرمستقیم در سند، ایمیل، صفحه یا tool response قرار می‌گیرد که سامانه برای انجام کار بازیابی یا پردازش می‌کند. در هر دو، ناوردا می‌تواند این باشد که متنِ فاقد اختیار نتواند دادهٔ دیگری را افشا یا عمل پایین‌دستی را مجاز کند. کنترل مستقیمِ مستقل، مجوز برنامه برای هر tool call است؛ کنترل RAG مستقل، اعمال ACL بر اساس کاربر پیش از retrieval و جلوگیری از عبور chunk بین tenantهاست. فیلتر یا برچسب «نامطمئن» مکمل‌اند، نه جایگزین این کنترل‌ها.

**صورت پرسش:** عاملی می‌تواند ایمیل بخواند و ارسال کند، اما کار موردنظر فقط خلاصه‌سازی است. دو کنترل متفاوت برای کم‌کردن خطر excessive agency شرح دهید و بگویید کدام‌یک باید در downstream اجرا شود.

**پاسخ پیشنهادی:** نخست، ابزار و credential را به خواندن محدود می‌کنم و قابلیت ارسال را اصلاً به عامل نمی‌دهم؛ این کاهش سطح اختیار است. اگر ارسال برای کار آینده لازم باشد، آن را به ابزار جدا با schema مقصد محدود، هویت همان کاربر و تأیید صریح انسان پیش از اجرای downstream تقسیم می‌کنم. مجوز نهایی باید در application یا سرویس ایمیل enforce شود، نه با تصمیم متنیِ خود مدل. ثبت tool call و نتیجهٔ واقعی نیز لازم است تا ادعای پاسخ مدل با اثر واقعی اشتباه نشود.

**صورت پرسش:** تفاوت data poisoning، خطای عادی برچسب و backdoor را با مثال سطح‌بالا توضیح دهید. برای یک dataset ثالث چه شواهد منشأ و چه آزمون رفتاری درخواست می‌کنید؟

**پاسخ پیشنهادی:** خطای برچسب می‌تواند بدون مهاجم و از خطای گردآوری/annotation ایجاد شود؛ poisoning زمانی است که عاملِ دارای هدف داده یا pipeline را برای تغییر خروجی یا دسترس‌پذیری دست‌کاری کند؛ backdoor رفتاری هدف‌دار است که ممکن است فقط با trigger خاص فعال شود. برای dataset ثالث، منبع و مجوز، revision و hash، تاریخ، روش گردآوری و تبدیل، هویت/دسترسیِ ناشر و زنجیرهٔ تحویل را می‌خواهم. سپس آزمون‌های کیفیت و رفتار را با سناریوهای ازپیش‌تعریف‌شده و دادهٔ نگه‌داشته‌شده اجرا می‌کنم و artifact نهایی را دوباره ارزیابی می‌کنم. hash یا signature تمامیت و منشأ را پشتیبانی می‌کند، نه قانونی‌بودن یا ایمنیِ محتوای آن.

**صورت پرسش:** در یک پروتکل مجاز، از ۱۲ تلاش معتبر برای یک هدف مشخص، ۳ مورد هدف را محقق می‌کنند. ASR مشاهده‌شده چیست؟ چرا از این نسبت نمی‌توان احتمال حمله به محصول یا نرخ شکست عمومی را نتیجه گرفت؟

**پاسخ پیشنهادی:** ASR مشاهده‌شده ۳/۱۲ = ۰٫۲۵، یا ۲۵٪ است؛ این تعبیر تنها در صورتی درست است که ۱۲ مورد واقعاً تلاش معتبر برای همان هدف و با قاعدهٔ موفقیت یکسان باشند. این نسبت به مجموعهٔ تلاش‌ها، نسخه، دسترسی، threat model و روش نمونه‌گیری وابسته است؛ promptهای تکراری ممکن است مستقل نباشند، و آزمونگر ممکن است هدف‌دار یا تطبیقی عمل کرده باشد. بنابراین ۲۵٪ نه احتمال حمله در محیط واقعی است و نه نرخ شکست همهٔ قابلیت‌ها یا نسخه‌های محصول. باید پوشش، severity، عدم‌قطعیت و محدودیت تعمیم هم گزارش شوند.

**صورت پرسش:** model extraction، membership inference و training-data extraction چه هدف‌های متفاوتی دارند؟ برای هرکدام یک کنترل یا آزمون متناسب پیشنهاد کنید و محدودیت آن را بنویسید.

**پاسخ پیشنهادی:** model extraction از خروجی queryها برای تقریب رفتار یا مدل استفاده می‌کند؛ membership inference دربارهٔ حضور یک رکورد مشخص در آموزش حدس می‌زند؛ training-data extraction دنبال آشکارشدن نمونه یا بخش memorized است. برای extraction می‌توان دسترسی، بودجهٔ query و پایش الگوی استفاده را کنترل کرد و میزان بازسازی را روی API مجاز سنجید؛ محدودیت این است که چندحسابی یا queryهای کم‌حجم ممکن است از یک سقف ساده عبور کنند. برای membership، ارزیابی attack مشخص با دادهٔ نماینده و کنترل داده/روش آموزش لازم است؛ پاسخ‌ندادن یک endpoint به پرسش membership، مقاومت آماری مدل را ثابت نمی‌کند. برای استخراج داده، حداقل‌سازی اطلاعات حساس، حاکمیت داده و آزمون نشتِ خروجی کمک می‌کند؛ نبود نمونه در چند query، نبود memorization یا افشا را اثبات نمی‌کند.

**صورت پرسش:** اقدام NIST AI 600-1 با شناسهٔ MS-2.7-007 چه نوع ارزیابی‌ای را پیشنهاد می‌کند؟ چرا نباید آن را گواهی الزامی یا تضمینِ مقاومت تلقی کرد؟

**پاسخ پیشنهادی:** اقدام MS-2.7-007 پیشنهاد می‌کند Red Teaming برای سنجش تاب‌آوری در برابر سوءاستفاده‌هایی که حمله به سامانه‌های دیگر را تسهیل می‌کنند، حمله‌های GAI مانند prompt injection، و حمله‌های ML مانند adversarial example/prompt، data poisoning، membership inference، model extraction و sponge examples انجام شود. NIST AI 600-1 یک پروفایل ریسک با اقدام‌های پیشنهادی است و خودش معیار قبولی یا گواهی اجباری برای هر محصول تعیین نمی‌کند. دامنه و روش باید با کاربرد، actor، نسخه و ریسک واقعی سازگار شود؛ یک run محدود نمی‌تواند دفاع در برابر همهٔ مهاجمان را تضمین کند.

**صورت پرسش:** پروژهٔ فصل ۶۴ صفر هدف محقق‌شده از شش مورد را گزارش می‌کند. دقیقاً چه نتیجه‌ای مجاز است و دست‌کم سه چیزی که از آن نمی‌توان نتیجه گرفت چیست؟

**پاسخ پیشنهادی:** نتیجهٔ مجاز این است که در همین fixture ساختگی، با سیاست ثابت کد، هر شش هدف شبیه‌سازی‌شده محقق نشدند و هفت نتیجه با خروجیِ موردانتظار fixture منطبق بود؛ یک درخواست سالم نیز مجاز ماند. نمی‌توان از آن مقاومت مدل در برابر prompt injection، امنیت محصول واقعی، privacy دفاع آماری، سلامت دادهٔ آموزش، نرخ موفقیت حمله در جهان واقعی، استقرارپذیری یا احتمال صفر رخداد را نتیجه گرفت. برنامه هیچ مدل، API، retrieval، ابزار بیرونی، pipeline، دادهٔ شخصی یا مهاجم واقعی را اجرا نمی‌کند. تست mutation فقط نشان می‌دهد خود fixture در چند شاخهٔ کد، با برداشتن کنترل متناظر، شکست مورد انتظار را آشکار می‌کند.

**صورت پرسش:** یک طرح آزمون مجاز برای agent متصل به RAG بنویسید که scope، هدف، ابزار، دادهٔ ساختگی، شاهد، معیار، قاعدهٔ توقف و کنترل مستقل را مشخص کند.

**پاسخ پیشنهادی:** scope کتبی را به محیط آزمایشی، agent نسخه‌مند، حساب آزمایشی و بازهٔ تعیین‌شده محدود می‌کنم؛ دسترسی به tenant یا سند واقعی ممنوع است. هدف این است که محتوای نامطمئنِ ساختگی نتواند سند خارج از مجوز را بازیابی کند یا ایمیل را ارسال کند. داده fixture شامل سند عمومی، سند tenant دیگر با نشانگر مصنوعی و یک دستور نامطمئن در متن است؛ ابزارها فقط جست‌وجوی fixture و ساخت draft را انجام می‌دهند و credential ارسال ندارند. شاهد شامل شناسهٔ نسخه و درخواست، مجوز retrieval، نتیجهٔ policy، tool call و پاسخ پالایش‌شده است. معیار، صفر دسترسی/ارسال خارج از scope در N تلاش تعریف‌شده و موفق‌بودن یک کنترل سالمِ خواندن عمومی است؛ این معیار را فقط برای همان fixture گزارش می‌کنم. با مشاهدهٔ هر دادهٔ واقعی، اثر بیرونی، افزایش بار غیرمنتظره یا عمل برگشت‌ناپذیر فوراً توقف می‌دهم. کنترل مستقل، ACL پیش از retrieval و منع ارسال در downstream است؛ پس از اصلاح، همان سناریو و یک مجموعهٔ تطبیقیِ مجاز را دوباره اجرا و ریسک باقی‌مانده را ثبت می‌کنم.

## یادداشت

این پاسخ‌نامه جایگزین مجوز، بازبینی امنیتی، مشاورهٔ حقوقی یا بررسی پیامد روی افراد نیست. اجرای [پروژهٔ فصل](../projects/64-red-team-lab/README.md) فقط رفتار چند شاخهٔ سیاستیِ fixture ساختگی را می‌آزماید؛ به گزارش [نتایج و محدودیت‌ها](../chapters/64-audit-report-fa.md) مراجعه کنید.
