# پاسخ‌نامهٔ مستقل فصل ۶۸ — امنیت عملیاتی، پایش و حریم خصوصی

این پاسخ‌ها نمونهٔ استدلال‌اند، نه تنها پاسخ ممکن. در طراحی واقعی، پروتکل، قرارداد provider، threat model، حوزهٔ قضایی و سیاست سازمانی باید جداگانه بررسی شوند.

## پرسش ۱

**صورت پرسش:** یک request دارای token معتبر اما `audience` نادرست است. کدام مرحله باید آن را رد کند و چرا پاسخ موفق endpoint دیگری مجوز دسترسی به این API نیست؟

**پاسخ:** Resource server یا لایهٔ اعتبارسنجی token باید پیش از اجرای handler، issuer و audience را با مقادیر مجاز همین API تطبیق دهد؛ token معتبر برای سرویس دیگر مجوز این resource server نیست. اعتبار امضا فقط ثابت می‌کند token با کلیدِ پذیرفته‌شده صادر شده، نه این‌که مقصد، scope، زمان و action آن با درخواست فعلی منطبق باشد. اگر credential برای این API معتبر نیست، پاسخ معمولاً 401 با challenge مناسب است؛ متن خطا نباید دادهٔ token یا جزئیات داخلی را آشکار کند. سپس authorization نیز باید action و منبع را جداگانه بسنجد.

## پرسش ۲

**صورت پرسش:** یک کاربر A شناسهٔ record متعلق به tenant B را در request قرار می‌دهد. سه نقطه‌ای را نام ببرید که باید object-level authorization را کنترل کنند و بگویید `tenant_id` ارسالی client را چگونه تفسیر می‌کنید.

**پاسخ:** سه مرز مفید برای کنترل دفاعی و آزمون عبارت‌اند از: middleware/API route که principal احرازشده را به request context متصل می‌کند؛ لایهٔ سرویس/domain که action و مالکیت object را پیش از اجرای عملیات می‌سنجد؛ و repository/data-access که query را با tenant معتبر scope می‌کند تا record نامجاز حتی از مسیر خطای برنامه خوانده یا تغییر داده نشود. این تکرار باید policy واحد و آزمون‌پذیر داشته باشد؛ frontend مرجع مجوز نیست. `tenant_id` ارسالی client یک ادعای نامطمئن است، نه هویت؛ tenant مؤثر از credential معتبر و context server-side گرفته می‌شود. پاسخ، cache، trace و log نیز نباید محتوای tenant B را افشا کنند.

## پرسش ۳

**صورت پرسش:** برای یک endpoint تولید تصویر، سه محدودیت متفاوت پیشنهاد کنید: یکی بر تعداد درخواست، یکی بر concurrency و یکی بر هزینهٔ server-side. توضیح دهید چرا یک limit بر اساس IP کافی نیست.

**پاسخ:** نمونهٔ آموزشی می‌تواند برای هر principal یا tenant سقف ۲۰ درخواست در دقیقه داشته باشد؛ حداکثر دو generation هم‌زمان مجاز کند؛ و برای هر کار، بودجهٔ server-side برآوردشده‌ای بر پایهٔ ابعاد، تعداد تصویر، steps یا هزینهٔ provider اعمال کند. عددها فقط نمونه‌اند و باید از workload و قرارداد provider سنجیده شوند. IP ممکن است چند کاربر پشت NAT را یکی بداند، با proxy یا جابه‌جایی تغییر کند، یا به‌وسیلهٔ client جعلی شود؛ بنابراین تنها یکی از signalهاست و نباید جای هویت معتبر، tenant، concurrency یا هزینه را بگیرد.

## پرسش ۴

**صورت پرسش:** Token bucket ظرفیت ۵ واحد دارد، با نرخ ۲ واحد بر ثانیه بازپر می‌شود و اکنون ۱ واحد دارد. پس از ۱٫۵ ثانیه، آیا درخواست با هزینهٔ ۴ پذیرفته می‌شود؟ فرض‌ها و سقف ظرفیت را نشان دهید.

**پاسخ:** اگر در فاصلهٔ مورد نظر درخواست دیگری اعتبار مصرف نکند، بازپرشدن برابر است با ۲ × ۱٫۵ = ۳ واحد. اعتبار پیش از درخواست ۱ + ۳ = ۴ می‌شود؛ این مقدار از سقف ۵ کمتر است و با هزینهٔ ۴ برابر است. پس درخواست پذیرفته و اعتبار به صفر می‌رسد. اگر درخواست هم‌زمان دیگری مصرف کرده باشد، باید state سازگارِ limiter ملاک باشد؛ فرمول به‌تنهایی race یا توزیع state را حل نمی‌کند.

## پرسش ۵

**صورت پرسش:** یک API سه 429 و یک 503 در یک دقیقه ثبت کرده است. چه اطلاعاتی برای تشخیص quota فردی از overload کل سرویس لازم دارید؟ چرا شمارش خام به‌تنهایی حمله را ثابت نمی‌کند؟

**پاسخ:** ابتدا مسیر و reason code، tenant یا principal به‌شکل مجاز و کمینه، زمان و `Retry-After` پاسخ‌های 429، درخواست‌های کل، queue depth، concurrency، latency، saturation و errorهای provider را با هم بررسی می‌کنم. 429 می‌تواند quota یک client باشد؛ 503 می‌تواند ناتوانی موقت سرویس یا وابستگی باشد، اما باید با علت داخلی و سلامت سامانه تطبیق داده شود. retry storm، رفتار معمول مشتری، misconfiguration و حمله می‌توانند شمارش مشابه بسازند. در نتیجه تعداد خام، بدون baseline، دامنه، علت، شواهد مستقل و بررسی انسانی، اثبات حمله نیست؛ شناسه‌های پرتعداد را هم به metric label تبدیل نمی‌کنم.

## پرسش ۶

**صورت پرسش:** برای یک request دارای prompt، token، tenant، action و response size، یک audit event کمینه طراحی کنید. چه فیلدهایی را ثبت نمی‌کنید و چه شناسه‌ای را برای correlation به‌کار می‌برید؟

**پاسخ:** یک schema ممکن است timestamp، شناسهٔ درخواستِ server-generated، pseudonymous principal در صورت نیاز، tenant در صورت ضرورت audit، action، resource type، outcome، reason code، نسخهٔ policy و نام سرویس اجراکننده را نگه دارد. مقدار دقیق response size فقط اگر هدف عملیاتی آن روشن باشد و به‌صورت bucket یا اندازهٔ کمینه ثبت شود. prompt، متن پاسخ، bearer token، Authorization header، secret، email، IP خام و attributeهای حساس را در log عمومی نمی‌نویسم؛ فهرست مجاز را ترجیح می‌دهم. برای correlation از request ID تصادفی و غیرمحتوامحورِ ساخته‌شده در server استفاده می‌کنم، نه hash سادهٔ prompt یا token.

## پرسش ۷

**صورت پرسش:** پس از مشاهدهٔ credential مشکوک، ترتیب containment، بررسی دامنه، rotation، recovery و اطلاع‌رسانی را بنویسید. کدام تصمیم‌ها به threat model و قانون/قرارداد وابسته‌اند؟

**پاسخ:** ابتدا incident owner و دامنهٔ سرویس/credential را مشخص می‌کنم و استفاده را با revoke یا محدودکردن scope مهار می‌کنم؛ شواهد مجاز و زمان‌ها را حفظ می‌کنم بی‌آن‌که secret را تکثیر کنم. سپس endpoint، audience، مجوزها، بازهٔ استفاده، tenantها و providerهای مرتبط را با log پالایش‌شده و منبع مستقل ارزیابی می‌کنم. پس از ابطال نسخهٔ مشکوک، credential تازه را با scope حداقلی از مسیر امن می‌چرخانم، وابستگی‌ها را به‌روزرسانی می‌کنم و recovery را با آزمون کنترل‌شده و پایش تأیید می‌کنم. این‌که چقدر سرویس را محدود کنیم، چه داده یا افرادی در معرض خطرند، چه زمانی به چه کسی اطلاع دهیم و کدام شاهد را نگه داریم، به threat model، حوزهٔ قضایی، قرارداد و مشاور مسئول وابسته است؛ نبود شاهد را نبود exposure فرض نمی‌کنم.

## پرسش ۸

**صورت پرسش:** Alert یک log pipeline متوقف شده را نشان می‌دهد، اما درخواست‌ها ظاهراً پاسخ می‌گیرند. چه شواهدی را جمع می‌کنید، چه چیزی را فرض نمی‌کنید و چگونه مشخص می‌کنید incident بسته شده است؟

**پاسخ:** ابتدا زمان شروع و دامنهٔ توقف، سلامت producer/queue/collector/storage، نرخ افت و تأخیر event، ظرفیت، تغییرات اخیر و clock skew را ثبت می‌کنم. با event ساختگی و مجاز مسیر end-to-end را می‌آزمایم و با metrics سرویس، لاگ‌های مستقلِ موجود و شواهد provider تطبیق می‌دهم. پاسخ‌گرفتن درخواست‌ها، کامل‌بودن audit را ثابت نمی‌کند؛ نبود رخداد در sink خراب نیز نبود incident یا دسترسی نامجاز را ثابت نمی‌کند. برای closure باید pipeline بازیابی و آزموده شده باشد، شکاف شواهد و اثر بالقوه با مالک ثبت شود، alert و کنترل اصلاح‌شده کار کنند، باقی‌ماندهٔ ریسک و تصمیم اطلاع‌رسانی صاحب مشخص داشته باشد و اقدام‌های post-incident دارای مسئول و موعد باشند.
