# پاسخ‌نامهٔ مستقل فصل ۶۰ — ردیابی آزمایش و ابزارهای MLOps

این پاسخ‌نامه پرسش‌ها را به‌صورت مستقل بازگو می‌کند. پاسخ‌ها معیارهای استدلال و مرز شواهد را نشان می‌دهند؛ برای یک محیط واقعی، سیاست داده، زیرساخت، نسخهٔ ابزار و مدل تهدید همان سازمان باید جایگزین فرض‌های مثال شود.

## ۱. پیکربندی یکسان و lockfile متفاوت

**پرسش:** یک آزمایش دو بار با `learning_rate` یکسان اجرا شده، اما lockfile در اجرای دوم فرق دارد. برای مقایسهٔ معتبر چه metadataهایی را ثبت و کدام تفاوت را نمی‌توان با هش fixture توضیح داد؟

**پاسخ:** هر اجرا باید commit و پاک/dirty بودن Git، هش diff در صورت dirty بودن، هش دقیق fixture و شناسهٔ snapshot، پیکربندی کامل، هش lockfile، نسخهٔ Python و سیستم‌عامل، digest image، نسخهٔ چارچوب‌ها و کتابخانه‌های مؤثر، seed و تنظیمات عددی/سخت‌افزاری را ثبت کند. در آن صورت می‌توان دید که برابری نرخ یادگیری فقط یک پارامتر را یکسان کرده است؛ اختلاف نسخه‌های وابستگی، الگوریتم kernel، dtype، nondeterminism یا device همچنان می‌تواند نتیجه را تغییر دهد. هش fixture تنها بایت‌های همان فایل داده را شناسایی می‌کند و چیزی دربارهٔ محیط اجرا یا نسخهٔ کد نمی‌گوید. برای انتساب علت، باید یک متغیر را تغییر داد و شرایط دیگر را تا حد امکان ثابت نگه داشت؛ حتی آن‌گاه باید دامنهٔ deterministic بودن را مستند کرد.

## ۲. دادهٔ مشتری و محدودیت ارسال

**پرسش:** دادهٔ مشتری اجازهٔ بارگذاری به tracker را ندارد. چه اطلاعاتی می‌توان ثبت کرد تا lineage حفظ شود، و چه چیزی نباید در log یا artifact کپی شود؟

**پاسخ:** در صورت مجاز بودن، می‌توان شناسهٔ داخلیِ غیرقابل‌حدس، نسخه یا شناسهٔ snapshot، هش محتوا، تعداد نمونه، schema، نام/نسخهٔ فرایند پاک‌سازی، split و شناسهٔ محل بازیابیِ کنترل‌شده را در metadata ثبت کرد. هش باید مطابق سیاست سازمان تولید و نگهداری شود؛ در بعضی زمینه‌ها هش پایدار خودش می‌تواند دادهٔ قابل‌پیوند باشد و نیازمند کنترل دسترسی است. نباید متن خام، ویژگی شناسایی‌پذیر، credential، مسیر داخلیِ حساس یا artifact مشتق‌شدهٔ قابل‌بازشناسایی در tracker عمومی/غیرمجاز کپی شود. مجوز، مقصد، access control، retention و مسیر حذف را پیش از اجرا بررسی می‌کنیم؛ هش نه رضایت است و نه مجوز.

## ۳. SQLite محلی، W&B آفلاین و نیازهای عملیاتی

**پرسش:** برای یک پژوهشگر منفرد بدون شبکه و یک تیم چندکاربره، کدام ویژگی‌های اجرای محلی SQLite و W&B آفلاین مفیدند و چه مسئله‌هایی را باید جداگانه حل کرد؟

**پاسخ:** SQLite محلی برای تمرین تک‌نفره، بازبینی run و ذخیرهٔ سادهٔ metadata مناسب است و W&B آفلاین می‌تواند run و Artifact را روی دیسک نگه دارد تا انتقال بعدی با تصمیم اپراتور انجام شود. هر دو برای آزمایش بدون اتصال به سرویس ابری کارآمدند. اما هیچ‌کدام به‌تنهایی اشتراک هم‌زمان امن، کنترل دسترسی سازمانی، backup/restore، رمزگذاری، retention، ظرفیت‌سنجی یا محل ذخیرهٔ مجاز را تضمین نمی‌کنند. SQLite یک پایگاه مشترک چندکاربرهٔ تولیدی فرض نمی‌شود. برای تیم باید tracker و artifact store مناسب، احراز هویت، egress، logging، پشتیبان‌گیری، حذف و نظارت جداگانه طراحی شود. انتقال W&B offline نیز باید پیش از `sync` از نظر داده و مقصد بررسی شود.

## ۴. tag متحرک و digest کانتینر

**پرسش:** Dockerfile از `python:3.13-slim` با tag متحرک استفاده می‌کند. برای بازسازی image چه چیزی را pin می‌کنید، و چرا pin کردن digest نیاز به وصلهٔ امنیتی آینده را حذف نمی‌کند؟

**پاسخ:** نسخهٔ Python را مشخص و image را با digest دقیق pin می‌کنیم؛ lock وابستگی‌های Python، platform/architecture و metadata کد/commit را نیز ثبت می‌کنیم. digest بایت‌های یک image را شناسایی می‌کند و مانع آن می‌شود که tag متحرک بی‌خبر به بایت دیگری اشاره کند. اما همان digest ممکن است بعداً آسیب‌پذیر تشخیص داده شود؛ pin کردن نسخه update را متوقف نمی‌کند و image را امن نمی‌سازد. باید releaseهای پایه را پایش کرد، digest تازه را review و scan کرد، آزمون را تکرار و image را آگاهانه rebuild/publish کرد. نمونهٔ فصل digest دارد، ولی image آن ساخته یا scan نشده است.

## ۵. خروجی Job پس از TTL

**پرسش:** Kubernetes Job موفق شده، اما `run.json` پس از TTL دیگر وجود ندارد. علت چیست و چه معماری ذخیره‌سازی/نگهداری باید پیش از اجرای مهم اضافه شود؟

**پاسخ:** manifest نمونه خروجی را روی `emptyDir` می‌نویسد؛ این volume به عمر Pod وابسته است. TTL نیز Job/Pod را پس از مدت مقرر پاک می‌کند، بنابراین فایل محلی همراه آن از بین می‌رود. پیش از اجرای مهم، باید PVC یا object store تأییدشده را mount/استفاده کرد، هویت و مجوز نوشتن/خواندن را تعریف کرد، artifact را با نسخه و هش ثبت کرد، و انتقال/restore را واقعاً آزمود. سیاست retention، backup، رمزگذاری و حذف نیز باید روشن باشد. `kubectl logs` یا وضعیت `Job Complete` جای artifact پایدار را نمی‌گیرد.

## ۶. API key در log

**پرسش:** در یک log، API key آشکار شده است. قدم‌های فوری شما برای محدودسازی دسترسی، چرخش credential، تعیین دامنهٔ افشا و رسیدگی به نسخه‌های artifact چیست؟

**پاسخ:** نخست credential را revoke/rotate می‌کنیم و دسترسی‌های مرتبط را محدود می‌سازیم؛ صرف حذف خط log کافی نیست. سپس scope، زمان، log store، دسترسی خوانندگان، cache، artifactها، CI output و نسخه‌های پشتیبان را طبق رویهٔ incident response مشخص می‌کنیم. اگر credential در image، Git یا نسخهٔ artifact باشد، همان نسخه‌ها را نیز پیدا و دسترسی/بازنشرشان را متوقف می‌کنیم و حذف یا quarantine را با ثبت شواهد انجام می‌دهیم. incident را به مسئول امنیت/حریم خصوصی ارجاع می‌دهیم و طبق الزام قانونی/سازمانی گزارش می‌کنیم. پس از رفع، محل secret را از log پاک/پنهان، capture را محدود، تست redaction اضافه و credential جدید را با دسترسی حداقلی صادر می‌کنیم؛ مقدار کلید را در گزارش incident بازنشر نمی‌کنیم.
