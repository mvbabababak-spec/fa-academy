# پاسخ‌نامهٔ مستقل فصل ۶۶ — API و FastAPI، قرارداد داده و محصول

**نگاشت:** فصل محلی ۵ جلد پنجم = فصل سراسری ۶۶. پاسخ‌ها دامنهٔ نمونه و قرارداد فصل را توضیح می‌دهند؛ آزمون ساختگی، ارزیابی پاسخ واقعی یا تأیید انتشار نیست.

## ۱. طول ورودی و قرارداد خطا

**صورت پرسش:** قرارداد `POST /v1/assist` برای پرسشی با طول ۳۰۱ نویسه چه status و media type خطایی می‌دهد، و کدام آزمون آن را تأیید می‌کند؟

**پاسخ:** اعتبارسنجی مدل `AssistRequest` مقدار بیش از `maxLength=300` را رد می‌کند. handler خطای اعتبارسنجی، status `422` و media type `application/problem+json` می‌دهد. آزمون `test_question_longer_than_contract_limit_is_rejected` در `test_api.py` همین مسیر را با ۳۰۱ نویسه و helper `assert_problem` بررسی می‌کند. این فقط رفتار محلیِ نسخهٔ آزموده‌شده را می‌سنجد.

## ۲. فیلد مفقود، null و خالی

**صورت پرسش:** تفاوت نبودن `locale`، مقدار `null` و رشتهٔ خالی چیست؟ برای هر وضعیت، رفتار موردانتظار را در schema و آزمون بنویسید.

**پاسخ:** در schema نمونه `locale` مقدار پیش‌فرض `fa` دارد؛ بنابراین اگر فیلد حذف شود، پاسخ فارسی انتخاب می‌شود. `null` با `Literal["fa", "en"]` سازگار نیست و باید با Problem Details و `422` رد شود. رشتهٔ خالی نیز عضو enum نیست و به همان مسیر رد می‌رود. اگر فیلد `question` باشد، نبودن، `null`، رشتهٔ خالی و رشتهٔ فقط‌فاصله وضعیت‌های جدا دارند: اولی/دومی/سومی در اعتبارسنجی ورودی رد می‌شوند و رشتهٔ فقط‌فاصله پس از trim با خطای دامنه رد می‌شود. قرارداد و آزمون باید این تمایز را صریح نگه دارند؛ آزمون‌های فعلی همهٔ این زیرحالت‌ها را نمی‌پوشانند و می‌توانند توسعه یابند.

## ۳. معنای GET و retry

**صورت پرسش:** چرا `GET /v1/catalog` نباید تغییری در state سرور ایجاد کند، و این قاعده چه اثری بر retry کلاینت دارد؟

**پاسخ:** RFC 9110، `GET` را برای دریافت representation تعریف می‌کند و آن را safe می‌داند؛ پس گرفتن فهرست نباید عمدتاً برای تغییر state سرور استفاده شود. درخواست دریافت معمولاً قابل‌تکرارتر از عملیات نوشتنی است، اما retry همچنان باید timeout، هزینه، محدودیت و سیاست کلاینت را رعایت کند. safe بودن روش تضمین‌کنندهٔ کیفیت پاسخ یا بی‌هزینه‌بودن سرویس نیست. این پروژه `GET` را فقط از fixture می‌خواند و state بیرونی ندارد.

## ۴. Schema در OpenAPI

**صورت پرسش:** در OpenAPI خروجی پروژه، `question` چه محدودیت طولی دارد و فیلدهای ناشناخته چگونه رفتار می‌کنند؟

**پاسخ:** schema درخواست `AssistRequest` در `/openapi.json` مقدار `maxLength` برابر ۳۰۰ را ثبت می‌کند. مدل `extra="forbid"` است، بنابراین property ناشناخته در body رد می‌شود. آزمون `test_openapi_documents_paths_bounds_and_problem_media_type` محدودیت و `additionalProperties: false` را وارسی می‌کند؛ آزمون `test_unknown_request_field_is_rejected_without_echo` نیز رفتار runtime را با sentinel می‌سنجد.

## ۵. درج پاسخ به‌صورت متن

**صورت پرسش:** پاسخ fixture دارای `<script>` را رابط چگونه نمایش می‌دهد، و آزمون browser چه چیزی را ثابت نمی‌کند؟

**پاسخ:** `demo.html` مقدار `answer` را به `textContent` می‌سپارد؛ رشتهٔ `<script>…</script>` بنابراین متن است و عنصر اجرایی نمی‌سازد. آزمون `test_success_loading_accessibility_and_small_viewports` نبودن عنصر `script` درون `#answer-text` و متن پاسخ را بررسی می‌کند. این آزمون فقط همین UI، مرورگر، fixture و مسیر را می‌سنجد؛ ممیزی جامع XSS، همهٔ ورودی‌ها، مرورگرها، screen readerها یا امنیت محصول نیست.

## ۶. پاسخ asynchronous و 202

**صورت پرسش:** چرا status `202` برای endpoint synchronous این آزمایشگاه نامناسب است؟ یک قرارداد مناسب برای job asynchronous چه شناسه یا مسیر تازه‌ای می‌خواهد؟

**پاسخ:** پاسخ نمونه همان درخواست را به‌طور synchronous از fixture حل می‌کند و بدنهٔ نهایی را می‌دهد؛ بنابراین status موفق معمول آن `200` است. `202 Accepted` نشان می‌دهد درخواست پذیرفته شده ولی پردازش کامل نشده است. یک قرارداد asynchronous باید شناسهٔ job، وضعیت جاری، راه دریافت نتیجه/خطا و معنای ماندگاری یا انقضا را تعریف کند؛ پیاده‌سازی صف و polling به فصل ۶۷ مربوط است.

## ۷. مرزهای خارج از پروژه

**صورت پرسش:** کدام بخش‌های احراز هویت، محدودیت نرخ، ثبت رخداد و استقرار عمداً از پیوست حذف شده‌اند، و در کدام فصل ادامه می‌یابند؟

**پاسخ:** پیوست نه هویت/مجوز، نه rate limiting، نه logging/monitoring/incident response و نه deployment/CI/CD پیاده‌سازی می‌کند. احراز هویت، محدودیت نرخ، ثبت رخداد، پایش، privacy و پاسخ به رخداد در فصل ۶۸ هستند؛ استقرار، نسخه‌بندی انتشار، CI/CD و بازگشت نسخه در فصل ۶۹. بهینه‌سازی runtime و صف/Cache در فصل ۶۷ است.

## ۸. محدودهٔ ادعای نتایج

**صورت پرسش:** نتایج ۱۲ آزمون API و ۲ آزمون مرورگر تا چه اندازه به ادعای کیفیت یک مدل واقعی اجازه می‌دهند؟ دو محدودیت آزمون را ذکر کنید.

**پاسخ:** این نتایج اجازهٔ نتیجه‌گیری دربارهٔ کیفیت مدل واقعی را نمی‌دهند؛ پروژه اصلاً مدل زنده ندارد و پاسخ‌ها از fixture ساختگی‌اند. نخست، TestClient اجرای ASGI را درون‌فرایندی می‌سنجد، نه شبکه، latency، ظرفیت یا deployment. دوم، آزمون مرورگر پاسخ API را intercept می‌کند و فقط چند state/viewport رابط را می‌سنجد، نه E2E واقعی، native mobile یا دسترس‌پذیری کامل. علاوه‌براین، fixture ساختگی و یک اجرای موفق، factuality، safety، privacy یا انطباق را ثابت نمی‌کند.
