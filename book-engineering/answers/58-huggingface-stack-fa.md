# پاسخ‌نامهٔ مستقل فصل ۵۸ — جلد چهارم، فصل محلی ۱۲

پاسخ‌های زیر نمونه‌اند، نه تنها راه‌حل معتبر. در کار واقعی، فرض‌ها، مجوز، نسخه، split و شاهد آزمون را کنار پاسخ بنویسید.

## ۱. گروه‌بندی نمونه‌های یک سند

واحد split باید چیزی باشد که دو نمونهٔ آن مستقل نیستند. اگر چند جمله از یک سند آمده‌اند، `group_id` را شناسهٔ سند یا منشأ قرار می‌دهم؛ اگر همان سند در چند نسخه/ترجمه آمده، هر نسخهٔ وابسته را به گروه بزرگ‌تری متصل می‌کنم. بعد گروه‌ها را، نه ردیف‌ها را، به train/validation/test می‌فرستم و شرط می‌گذارم:

```python
assert not (train_group_ids & validation_group_ids)
assert not (train_group_ids & test_group_ids)
assert not (validation_group_ids & test_group_ids)
```

اگر سندها بسیار نامتوازن باشند، تقسیم گروهی ممکن است نسبت کلاس‌ها را تغییر دهد؛ راه‌حل این نیست که نمونه‌های هم‌بسته را تصادفی پخش کنیم. می‌توان از الگوریتم group-stratified مناسب، seed ثبت‌شده یا split زمانی/منشأمحور استفاده کرد و توزیع کلاس را جدا گزارش داد. باید معلوم باشد معیار استقلال بر اساس سند، شخص، کاربر، خانوادهٔ prompt یا بازهٔ زمانی تعریف شده است.

## ۲. افزودن دو سطر validation

ابتدا دو `example_id` یکتا و یک `group_id` تازه برای validation انتخاب می‌کنم؛ هیچ‌یک از گروه‌های train را دوباره به validation نمی‌دهم. فایل JSONL را دقیقاً یک ردیف در هر خط و UTF-8 نگه می‌دارم. سپس `record_count`, `split_record_counts`, `split_group_counts` و `label_counts` را در `fixture_manifest.json` به‌روز می‌کنم و SHA-256 بایت‌های واقعی فایل را دوباره محاسبه می‌کنم. آزمون hash باید در صورت تغییر ناخواسته fail شود.

در کد اجرا، tokenizer با `train_rows` ساخته می‌شود؛ ردیف‌های تازهٔ validation وارد `train_from_iterator` نمی‌شوند. پس از تغییر، `python -m unittest discover -v`, CLI و گزارش خروجی را دوباره اجرا می‌کنم. افزایش validation به ۶ ردیف، به‌تنهایی نمونهٔ کافی یا معیار معتبر برای ارزیابی کیفیت نمی‌سازد؛ این فقط fixture تمرینی است.

## ۳. فایل‌های لازم برای بارگذاری محلی

ابتدا model card را از نظر task، معماری، زبان/دامنه، مجوز، منبع داده، محدودیت‌ها، کد همراه و revision بررسی می‌کنم و commit کامل را ثبت می‌کنم. فایل‌های لازم بسته به tokenizer/model فرق دارند؛ ممکن است `config.json`, یک وزن مثل `model.safetensors`, فایل `tokenizer.json` یا vocab/merges، `tokenizer_config.json` و special-token metadata لازم باشند. فهرست واقعی را از همان repo و loading code می‌گیرم، نه از یک checklist ثابت.

فایل‌ها را فقط پس از دسترسی مجاز، به cache یا پوشهٔ کنترل‌شده دانلود می‌کنم؛ commit و SHA-256 می‌نویسم و سپس بارگذاری را با `revision=<commit>` و `local_files_only=True` در محیط شبکه‌بسته می‌آزمایم. اگر artifact یا کد اختصاصی model لازم باشد، آن را جدا بازبینی می‌کنم؛ token دسترسی در مخزن یا log نمی‌رود.

## ۴. Dataset map-style در برابر streaming

`Dataset` map-style را برای داده‌ای می‌خواهم که index پایدار، تبدیل چندباره، shuffle/دسترسی ردیفی و cache محلی مفید است و اندازه/ذخیره‌سازی اجازه می‌دهد. `IterableDataset` زمانی جذاب است که داده خیلی بزرگ یا جریان ورودی باشد و قرار است ترتیبی پردازش شود. در streaming معمولاً نمی‌توان هر ردیف دلخواه را با index تصادفی برداشت؛ retry، resume، ترتیب shard و موارد تکراری هم اهمیت دارند.

shuffle با `buffer_size` نمونه‌های موجود در buffer را جابه‌جا می‌کند، اما اگر کل مجموعه داخل buffer نباشد، تضمین permutation سراسری نمی‌دهد. بنابراین seed، اندازهٔ buffer، shardها و ترتیب epoch باید ثبت شوند. برای نسخه و قالب دقیق، روی نمونهٔ کوچک رفتار API را امتحان می‌کنم و `IterableDataset` را با `Dataset` هم‌معنا فرض نمی‌کنم.

## ۵. اجرای remote code کنار کلید cloud

یک threat model ساده می‌گوید code از maintainer بیرونی می‌آید، اما process به فایل‌ها، متغیرهای محیطی یا سرویس‌های cloud دسترسی دارد. کنترل‌ها:

1. `trust_remote_code=True` را پیش‌فرض نکنم؛ revision کامل را pin و کد را قبل از اجرا مرور کنم.
2. آزمون اولیه را در container/VM موقت با user غیرریشه، filesystem محدود و بدون token/credential سازمانی انجام دهم.
3. شبکهٔ خروجی را ببندم یا به مقصدهای ضروری محدود کنم؛ artifactهای دریافت‌شده را scan/hash کنم.
4. اگر لازم است Hub token استفاده شود، read-only و کم‌اختیار باشد و از secret manager inject شود؛ log و command history را بررسی کنم.
5. وزن را در صورت پشتیبانی از `safetensors` بارگذاری کنم؛ این کار ریسک pickle را کاهش می‌دهد، ولی جای بررسی کد، منبع یا رفتار مدل را نمی‌گیرد.

باید همچنین license و سیاست داده را مستقل مرور کرد. public repo به معنی مجوز استفاده در محصول یا واردکردن داده به cloud نیست.

## ۶. مقایسهٔ اجرای ۲ و ۳ گام

برای مقایسهٔ سالم، همان hash fixture، همان نسخه‌ها، `seed=58`, همان device، batch size و config را حفظ می‌کنم و فقط `max_steps` را تغییر می‌دهم. اجرای فعلی با دو گام روی Linux/CPU lossهای `0.6931533` و `0.6891557` داده است؛ با سه گام، دو مقدار اول باید در همان محیط و نسخه‌ها ثابت بمانند و گام سوم مقدار تازه‌ای ثبت کند. بین دستگاه‌ها، نسخه‌ها یا محاسبات عددی متفاوت، برابری بیت‌به‌بیت تضمین‌شده نیست.

کم‌شدن یا زیادشدن loss روی چند مثال ساختگی نه به‌تنهایی کیفیت است و نه دلیل تعمیم. مدل از وزن تصادفی شروع می‌کند، validation فقط smoke loss دارد و test مستقل/کاربر واقعی نداریم. نتیجهٔ درست این تمرین ثبت trace، hash و محدودیت است؛ نه انتخاب «مدل بهتر».

## ۷. انتخاب Trainer یا Accelerator

برای classifier استاندارد که loss و training loop مرسوم دارد، ابتدا `Trainer` را بررسی می‌کنم: argumentها، save/eval cadence، معیار، callback و backend را صریح تنظیم و smoke test می‌کنم. مزیتش کاهش کد تکراری است؛ خطرش این است که پیکربندی و lifecycle را نخوانده، به پیش‌فرض‌هایش تکیه کنم.

اگر loss چندبخشی، مرحله‌های سفارشی یا داده‌گیری خاص دارم، ممکن است حلقهٔ دست‌نویس با `Accelerator` مناسب باشد. باید model/optimizer/loader را طبق API یک‌بار با `prepare` آماده کنم، `backward` را درست صدا بزنم و gradient accumulation, checkpoint, evaluation, scheduler, mixed precision و distributed behavior را خودم آزمون کنم. انتخاب نهایی را بر اساس قابلیت نگه‌داری و محدودیت پروژه مستند می‌کنم؛ `Trainer` را دوباره با `Accelerator.prepare` نپیچم مگر API نسخهٔ مشخص چنین استفاده‌ای را مستند کند.
