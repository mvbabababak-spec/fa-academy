# پروژهٔ فصل ۶۷: صف، microbatch و cache پاسخ دقیق

این پروژه یک شبیه‌ساز قطعی و رویدادمحور برای **یک worker فرضی** می‌سازد. چهار پیکربندیِ بدون batch، microbatch، cache پاسخ دقیق، و ترکیب دو روش را روی trace ساختگی ۲۴درخواستی مقایسه می‌کند. ۱۲ شناسهٔ درخواست یکتا در burst نخست تکرار می‌شوند؛ burst دوم پس از تکمیل فرضی پاسخ‌های نخست می‌رسد. تمام زمان‌ها، tokenها، پاسخ‌ها، ظرفیت‌ها و ضرایب سرویس اختراعی‌اند.

این پروژه **مدل زبانی یا runtime را اجرا نمی‌کند**، به GPU یا شبکه دست نمی‌زند و benchmark سخت‌افزاری نیست. پاسخ «مدل» در شبیه‌سازی رشتهٔ مرجعِ fixture است؛ بررسی برابری آن فقط یک کنترل انتقال/تمامیت fixture است و **کیفیت، درستی، ایمنی یا سودمندی مدل را نمی‌سنجد**.

## محیط و اجرا

- CPython 3.13.16، کتابخانهٔ استاندارد؛ وابستگی ثالث ندارد.
- `synthetic_serving_trace.json` دارای ۲۴ درخواست و ۱۲ کلید دقیق ساختگی است؛ SHA-256: `2082e82cc4e68ec031715c6429c225cf06e77124fe2c565fe397613fbbbf7e0c`.
- منشأ، تعداد و هش ورودی در `fixture_manifest.json` آمده‌اند؛ محیط و مرز اجرا در `environment.json` و خروجی قطعی در `results.json` ثبت شده‌اند.

از ریشهٔ مخزن:

```bash
(cd book-engineering/projects/67-serving-lab && python -m unittest -v)
python book-engineering/projects/67-serving-lab/serving_lab.py \
  --fixture book-engineering/projects/67-serving-lab/synthetic_serving_trace.json \
  --output /tmp/ch67-results.json
cmp /tmp/ch67-results.json book-engineering/projects/67-serving-lab/results.json
```

## مدل شبیه‌سازی

- صف FIFO با سقف ۸ درخواستِ **منتظر**؛ batch در حال اجرا از این شمار جداست. ورود پس از پرشدن صف با وضعیت داخلی `rejected_queue_full` رد می‌شود؛ این نام، پاسخ HTTP تولیدی یا سیاست محدودیت نرخ نیست.
- حداکثر batch چهار درخواست است. زمان انتظار جمع‌کردن batch حداکثر ۱۲ ms است؛ اگر batch زودتر پر شود، همان لحظه dispatch می‌شود.
- prefill فرضی از سربار ثابت ۵ ms به‌علاوهٔ ۰٫۴ ms به‌ازای بیشترین prompt در batch ساخته می‌شود. گام decode فرضی ۴ ms به‌علاوهٔ ۰٫۷۵ ms برای هر دنبالهٔ افزوده است. batch تا پایان خروجی طولانی‌ترین عضو worker را درگیر نگه می‌دارد.
- cache فقط پاسخ **دقیقاً برابرِ کلید canonical** را بازمی‌گرداند؛ lookup برابر ۱٫۵ ms فرض شده است. کلید شامل revision مدل، شناسهٔ prompt، پارامترهای decoding، locale و revision زمینه است. سقف ۱۶ ورودی و ۴٬۰۹۶ بایت برای مجموع UTF-8 کلید و بدنه اعمال می‌شود؛ eviction از نوع LRU است.
- latency پاسخ از ورود تا پاسخ کامل است. `model_ttft_p95_ms` و `queue_wait_p95_ms` فقط درخواست‌های محاسبه‌شده را دربرمی‌گیرند؛ latency پاسخ هم مسیر مدل و هم cache hit را شامل می‌شود. percentile با روش nearest-rank است.
- deadline برابر ۱۸۰ ms فقط برای شمردن پاسخ دیرهنگام استفاده می‌شود؛ لغو درخواست و آزادکردن محاسبهٔ دیرشده پیاده‌سازی نشده‌اند.

کلید fixture از شناسهٔ prompt ساختگی استفاده می‌کند، نه متن واقعی یا hash یک prompt واقعی. در محصول باید همهٔ ورودی‌های مؤثر بر پاسخ، freshness و invalidation، و مرز کاربر/مستأجر جداگانه طراحی و آزموده شوند. موارد حریم خصوصی/احراز هویت و telemetry در این آزمایشگاه پیاده‌سازی نمی‌شوند.

در همهٔ runها، خروجی ثبت‌شدهٔ پاسخ با رشتهٔ مرجع fixture برابر بود؛ در مسیر model-miss، شبیه‌ساز رشتهٔ مرجع را مستقیماً از fixture می‌گیرد، بنابراین این تطبیق به‌صورت پیش‌فرض برقرار است و آزمون مستقلِ انتقال نیست. آزمون برخورد کلید نشان می‌دهد پاسخ cacheشدهٔ متفاوت را می‌توان ناسازگار علامت زد. این اعداد کیفیت مدل را نمی‌سنجند. بیشینهٔ صفِ منتظر در این trace ۸ بود؛ cache ترکیبی در نقطهٔ اوج فقط ۲٬۴۶۰ بایت payload برآوردشده نگه داشت. خروجی تفصیلی در `results.json` است.

این اعداد فقط نتیجهٔ چهار اجرای **همین trace و همین مدل سرویس فرضی** هستند. نرخ پاسخ بر ثانیه از کل بازهٔ مصنوعی، شامل فاصلهٔ زمانی دو burst، محاسبه شده است؛ آن را ظرفیت واقعی یا برتری یک محصول ندانید. پیکربندی microbatch نسبت به baselineِ همین فرض‌ها رد صف و deadline miss کمتری داشت، اما از یک اجرای قطعی نمی‌توان سود یا trade-off عمومی نتیجه گرفت.

## محدودیت‌ها

- trace، token count، prompt ID، خروجی، زمان، ظرفیت و deadline کاملاً ساخته‌شده‌اند و دادهٔ کاربر، trace تولیدی یا مدل واقعی نیستند.
- مدل زمان، یک worker و رفتار سادهٔ batch را نشان می‌دهد؛ تفاوت runtime، GPU، continuous batching، نرخ تصادفی ورود، توزیع service time، streaming token، هم‌زمانی شبکه، confidence interval و بار چندساعته را اندازه نمی‌گیرد.
- برابری رشته با fixture، quality metric نیست؛ هیچ داوری انسانی یا ارزیابی فصل‌های ۶۲–۶۳ اجرا نمی‌شود.
- بایت cache فقط طول UTF-8 کلید و پاسخ است و سربار Python، allocator، index و حافظهٔ پردازه را شامل نمی‌شود؛ این برآورد حافظهٔ GPU یا KV cache نیست. دربارهٔ KV/prefix cache و runtime به فصل ۶۱ رجوع کنید.
- freshness، invalidation بر اساس تغییر داده/مدل، cache شخصی یا چندمستأجری، authorization، rate limiting، ثبت رخداد، monitoring، cancellation، retry، deployment و autoscaling خارج از دامنه‌اند؛ فصل‌های ۶۸ و ۶۹ مرزهای محصول و عملیات را ادامه می‌دهند.

در یک سرویس واقعی، پیش از تنظیم batch یا cache، workload مجاز و نماینده را تعریف کنید؛ ابتدا correctness و کیفیت را با معیار مستقل کنترل کنید؛ سپس نرخ ورود، concurrency، توزیع طول، queue depth، p50/p95/p99، رد/timeout، مصرف واقعی حافظه و بازهٔ اندازه‌گیری را ثبت کنید. نمونهٔ این مخزن صرفاً برای فهم فرض‌ها و رفتار صف است، نه جایگزین آن آزمون‌ها.
