# پروژهٔ فصل ۴۲: طراحی و بودجه‌بندی Mini GPT

این پروژه فصل ۳۷ را از نو پیاده‌سازی نمی‌کند. آن پروژه همین حالا یک Decoder-only کوچک با embedding توکن/موقعیت، بلوک علّی و خروجی `[batch, sequence, vocabulary]` دارد؛ اسکریپت حاضر همان مدل آزموده‌شده را import می‌کند و روی سه پرسش فصل ۴۲ تمرکز می‌کند: شمار دقیق پارامتر برای پیکربندی انتخابی، رشد اندازهٔ تنسورهای مهم با طول زمینه، و تخمین‌های شفافِ حافظهٔ وزن/گرادیان/حالت AdamW. کد فقط یک forward تصادفی می‌زند؛ **آموزش یا سنجش کیفیت انجام نمی‌دهد**.

## نیازمندی و اجرا

- Python 3.11+ و PyTorch 2.6.x؛ CPU کافی است.
- مدل Decoder-only مشترک در `../37-encoder-decoder/transformer_architectures.py` است؛ فایل آن تغییر نمی‌کند.
- از ریشهٔ مخزن:

```bash
python -m unittest discover -v --start-directory book-engineering/projects/42-mini-gpt-design
python book-engineering/projects/42-mini-gpt-design/mini_gpt_design.py --context-sweep
```

یا از همین پوشه:

```bash
python -m unittest discover -v
python mini_gpt_design.py --context-sweep
```

پروژه هیچ داده یا checkpointی از شبکه نمی‌گیرد. مقادیر پیش‌فرض با `V=102`, `C=64`, `d=64`, `h=4`, `f=256`, `L=2` و batch برابر ۱۶ هستند. آن‌ها فقط نقطهٔ طراحیِ قابل‌اجرا برای درس‌اند؛ توصیهٔ ظرفیت برای فارسی یا LLM تولیدی نیستند.

## قرارداد شمارش و تخمین

شمار پارامترها دقیقاً با ساختار موجود در فصل ۳۷ تنظیم شده است: embedding توکن و موقعیت، `nn.MultiheadAttention` با bias، دو LayerNorm در هر block، FFN دوخطی با bias، LayerNorm نهایی و head واژگانِ **جدا از** embedding ورودی. بر این مبنا، تنظیم پیش‌فرض باید دقیقاً ۱۱۷٬۳۵۰ پارامتر داشته باشد. اگر معماری، نسخهٔ ماژول یا تنظیمات عوض شود، آزمون مقایسهٔ فرمول با `model.parameters()` باید هشدار بدهد.

تخمین پایدار پیش‌فرض برای FP32 شامل وزن‌ها (۴ بایت/پارامتر)، گرادیان‌ها (۴ بایت) و دو moment از AdamW (۸ بایت در مجموع) است: ۱۶ بایت برای هر پارامتر، زمانی که stateهای optimizer ساخته شده‌اند. شکل score-equivalent، activation پنهان FFN و logits جداگانه گزارش می‌شوند؛ جمعشان فقط اندازهٔ چند tensor مرجع است، **نه اوج حافظه**. این اعداد allocator، workspace، residualها، گرادیان activation، padding و اثر kernel بهینه را ثبت نمی‌کنند. برای اندازه‌گیری واقعی، همان batch/config را روی سخت‌افزار هدف با profiler/allocator مناسب آزمایش کنید.

`--context-sweep` طول‌های ۳۲، ۶۴ و ۱۲۸ را مقایسه می‌کند. جدول نشان می‌دهد پارامترهای position embedding با `C` خطی زیاد می‌شوند، اما tensor معادل score متراکم با `T²` رشد می‌کند. هیچ زمان اجرا یا برتری کیفیتی اندازه‌گیری نمی‌شود. smoke test عمداً هر ردیف را با یک token غیر-padding شروع می‌کند؛ اگر query اول هم از causal mask و هم از padding mask کلید نبیند، در PyTorch 2.6.0+cpu خروجی non-finite مشاهده شد. `build_model` پروژه یک guard بی‌پارامتر روی مدل فصل ۳۷ می‌گذارد: prefix چپ‌pad/all-pad و ماسک‌شدن جایگاه آغاز را رد می‌کند، ولی right-padding را با prefix معتبر می‌پذیرد. برای دادهٔ واقعی از BOS/پیشوند معتبر آغاز کنید و finite بودن را روی backend خود بسنجید؛ خود مدل فصل ۳۷، بدون این guard، این edge case را رد نمی‌کند.

## آزمون‌ها و مرزها

۱۱ آزمون، فرمول شمار پارامتر را با مدل فصل ۳۷ تطبیق می‌دهند، خروجی را در شکل `[N,T,V]` کنترل می‌کنند، تغییر توکن آینده را برای logits پیشین می‌آزمایند، right-padding و finite بودن را بررسی می‌کنند، prefix چپ‌pad/all-pad و ماسک‌شدن BOS را رد می‌کنند، و برآورد هزینه‌ها را می‌سنجند. این‌ها قرارداد معماری و حساب را می‌سنجند؛ آموزش، تعمیم، perplexity، کیفیت تولید، سرعت یا مصرف اوج GPU را اثبات نمی‌کنند.

هنگام ساخت batch واقعی، ورودی `x[t:t+T]` و هدف `x[t+1:t+T+1]` باید یک‌خانه جابه‌جا باشند. `key_padding_mask` کلیدهای padding را می‌بندد، اما loss روی targetهای padding باید جداگانه نادیده گرفته شود. اگر سندها را در یک stream بسته‌بندی می‌کنید، وجود EOS به‌تنهایی مانع توجه سند دوم به سند اول نیست؛ برای استقلال سندها ردیف جدا یا mask بلوکی لازم است. آماده‌سازی corpus و مرزهای داده در فصل‌های ۴۰ و ۴۳ است؛ آموزش کامل در فصل ۴۴.
